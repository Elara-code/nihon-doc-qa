## Day 16-17：Streamlit 界面

### 设计思路（这套话面试时可以直接讲）
- 不做前端炫技。**RAG 应用的 demo 界面价值在"能立刻演示"，不在 UI**。
- 关键要素只有四个：**文档上传** / **模式切换** / **提问** / **回答+出处**。
- 加了一个"检索命中段落"的展开块——这是让面试官**一眼相信"真的基于检索"**
  的关键，而不是"LLM 凭印象答的"。

### 工程要点
- `@st.cache_resource` 缓存 pipeline，避免每次 rerun 重载 bge-m3 / reranker。
- 模式切换是**热切换**：直接改 `pipeline.retriever.mode`，无需重建索引。
  → 这让 demo 时同一题切模式对比成本极低（参见 `demo-script.md`）。
- 上传文件落到 `tempfile.mkdtemp` 临时目录再入库，不污染 `samples/`。

## Day 18-19：评估

### 为什么不只用关键词命中
关键词命中是 Week 3 用的"粗筛"——零成本，但有两个坑：
- **同义词/释义**：答案对但用词不同会判错。
- **跨语言回答**：中文问、日文答（或反过来）容易被关键词逻辑误伤。

所以 Day 18 加了 **LLM-as-judge**：让同款 deepseek-chat 当裁判，按
"答案是否实质回应问题、与参考关键词语义一致"打 0/1，
`response_format=json_object` 强约束输出，单题失败不影响整体。

### 工程要点
- 两种判分**并存**：报告里同时显示关键词命中率和 LLM 通过率，互为印证。
- LLM 裁判可关：`--judge keyword` 退化为零成本评估，CI 友好。
- 三模式横向：`--all-modes` 一次跑完 vector / hybrid / rerank。

### 用法

```bash
# 最快：当前模式 + 关键词命中
python eval/evaluate.py

# 横向对比 + LLM 裁判（推荐放进作品集的版本）
python eval/evaluate.py --all-modes --judge llm
```

### 准确率（实测）

测试集 12 题（中日双语，文档 `houkokusho_sample.pdf`，264 chunk）：

| 模式 | 关键词命中率 | LLM 裁判通过率 |
|------|------|------|
| vector | 67% (8/12) | 83% (10/12) |
| hybrid | 75% (9/12) | 92% (11/12) |
| rerank | **92% (11/12)** | **92% (11/12)** |

**关键观察**：

1. **vector → rerank：关键词 +25 pp，LLM 裁判 +9 pp**。两个判分方式都指向
   rerank 是赢家，互为印证。
2. **vector 67 vs 83 的 gap**：LLM 裁判识别出 4 个"答案对但用词与关键词不同"
   的回答（Q7、Q10、Q11 等），说明关键词命中会**低估真实表现**。在生产环境
   这就是为什么不能只用关键词指标做评估。
3. **rerank 的两个数字一致 (92/92)**：回答和关键词已经高度对齐，LLM 也"挑不出"
   额外的对答案。这是一个判分方式收敛的健康信号。
4. **新发现：Q4 JNLA 在 rerank 反而退步**（hybrid ✅ → rerank ❌）。
   和 Week 3 诊断的 Q7「主题混杂 chunk」**同一个根因**——JNLA 答案也藏在
   chunk #8 末尾，rerank 这次把另一个 chunk 排到它前面。Q7 这次被救回来了，
   失败转移到了 Q4——说明「主题混杂 chunk」问题是结构性的，不是偶发，
   `week3-notes.md` 中列的生产环境修复路径仍然成立。
